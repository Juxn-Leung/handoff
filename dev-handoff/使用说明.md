# 腾讯文档个人账号共享工单

协作者分别使用自己的个人 QQ／微信账号、自己的 Token 和自己的代码仓库，共享同一张腾讯智能表。日常在 AI 聊天中操作，不必手动运行脚本。

**AI 完成开发后停在“待验收”，并默认启动原工作区自动回写；验收人说“验收工单 ID”，AI 按表逐项检查，全部通过就确认、有明确失败就退回，无法验证项列出原因。确认后原工作区自动复核并回写“已完成”，无需处理人再说一次回写。“继续”不代表验收确认。**

## 1. 安装

使用 npm / npx 从 Git 仓库安装，无需下载安装包：

```sh
# Codex，当前项目
npx skills@latest add Juxn-Leung/handoff --skill dev-handoff -a codex
# Claude Code，当前项目
npx skills@latest add Juxn-Leung/handoff --skill dev-handoff -a claude-code
```

加 `-g` 可安装为个人通用技能。安装需要 Node.js 22.20+；skills CLI 会安装完整的 scripts、references 和 agents。

已有安装在原项目运行 `npx skills@latest update dev-handoff -p`，全局安装改用 `-g`，然后让 AI 重新读取已安装的 SKILL.md。日常业务验收和双方可复制话术见第 5.1 节；仅验证技能协议的双账号联调见第 5.2 节。

需要 Python 3.10+、Git 和能访问腾讯文档的网络。下面用 Codex `$dev-handoff` 举例，Claude Code 换成 `/dev-handoff`。

安装完成后按下一节建表或接入。需要授权时，AI 会生成本人的网页授权链接：用自己的微信或 QQ 登录，点击“确认授权”，显示“已授权”后回到聊天回复“已授权”，AI 就会继续原来的操作。Token 自动保存在本人电脑，不需要贴进聊天。

详细安装和授权排查见 [setup.md](references/setup.md)。

## 2. 一人建表，邀请指定同事

任意一人输入：

```text
$dev-handoff 建表 订单项目，不限定分工
```

也可以在建表时指定“分工选项为：前端、后端、测试”，或其他自定义名称。分工是成员说明，不限制领取；默认可自由填写或留空。

返回的腾讯智能表包含：

| 工作表 | 用途 |
|---|---|
| 工单 | 发布人、跟进人、状态、交接说明、验收标准、依赖和处理结果 |
| 跟进记录 | 领取、分配、开始、阻塞、退回、待验收、验收通过的历史事件 |
| 成员 | 每位协作者登记的稳定账号 ID、姓名和可选分工 |

建表会尝试整理默认工单视图，只显示日常业务字段；若平台拒绝，会明确报告表头待整理，不重复建表。目标是：账号 ID、版本、证据与恢复字段隐藏，AI 仍可读写。原始说明、来源、关联和验收信息可通过工单详情查看。

建表人在腾讯文档右上角“分享”面板添加同事使用的个人账号，设为“可编辑”，自己把链接发给同事。不必把表格改成所有人可编辑，也不要共享 Token。

另一位同事在自己的开发仓库只需输入：

```text
$dev-handoff 接入 <真实腾讯智能表URL>
```

首次接入时打开 AI 返回的授权链接，使用被邀请的账号确认授权，再回复“已授权”。AI 自动完成账号检查、绑定、成员登记和队列检查，最后展示接入结果。已授权时直接完成；不需要再逐步输入“绑定”“加入”“查看成员”。

新绑定的别名默认使用“开发对接”，已有绑定沿用原别名，也可在指令中指定“别名为订单项目”。分工默认留空；如果表格要求固定选项，AI 才询问。初建表的一方也加入；需要时可随时用“查看成员”核对。

**表格编辑权限决定能否读写，成员和跟进人 ID 决定由谁处理，两者分别设置。**

## 3. 后端发布，前端领取

以后端实现订单接口、前端接入页面为例。后端先在编辑器里暂存本次交接的代码，再输入：

```text
$dev-handoff 发布 订单项目
```

AI 读取暂存版本，按独立接入和验收的事项拆单，写清路径与方法、鉴权、请求参数、响应、错误处理、示例、联调可用性和验收标准。有关键缺口会先问，不自动暂存、提交、推送或部署。

每单明确影响应用、接手方交付、验证证据提供方和验收责任。能独立验收的应用分别成单，公共修改尽早明确归属；后端回归测试是变更来源时，不直接照抄为前端的全部验收标准。真实联调是否是本单必要条件，要在发布时约定，不能在做完后缩小范围。

新工单还要从共享成员中明确实际验收人，并把每项验收标准关联操作步骤、预期结果和检查项目。同名成员用稳定账号区分，不用分工代替身份。

AI 发布前检查应用和共享契约重叠，接手方再用自己仓库的计划文件预检。提示用于调整拆单或安排顺序，不自动建立依赖，也不放松待验收保护。

发布后工单状态是“待对接”，跟进人先留空。前端输入：

```text
$dev-handoff 查看 订单项目
$dev-handoff 查看 订单项目，只看 admin-app
$dev-handoff 领取 <工单ID>
```

AI 可以领取前置依赖已完成且没有其他跟进人的事项，不按前端、后端或其他分工限制。也可以由后端输入“把工单 X 分配给前端”，AI 从成员表解析唯一账号 ID 后分配。相同昵称要按 ID 消歧，不默认选第一位。

队列默认最多 20 条摘要，显示范围、标题、状态、阻塞原因和下一步，并报告总数与剩余条数。按应用筛选也会包含全局共享事项；范围未知的旧工单单独提醒，不猜测应用。需要完整需求时查看工单，验收时查看结果证据。

反向对接同样可用：前端发布待后端实现的接口需求，后端领取。发布说明要明确标注实现与可用状态。

## 4. 每次处理一条

领取后输入“处理工单 X”。AI 阅读完整说明和交付约定，核对当前仓库能否承接，提前预检计划文件，成功开始后再修改代码。也可输入“预检这一组事项”，提前找出公共字典等共享文件；预检本身不领取或开始。扩大范围前先检查，不能自动跨仓库修改。

完成代码与适当验证后，AI 写入“待验收”，为有指定验收人和逐项标准的业务单启动本机自动回写，展示结果、验证记录、结果版本、实际后台进程状态、队列数量和下一条建议，随后停止开发。若想保留手动回写，可在处理时说明“这单手动回写”，AI 提交时会关闭本轮自动回写。

这时回复“继续”可以处理下一条独立事项。它不会把前一条自动验收。前置工单尚未验收、文件重叠、公共契约影响尚未核清时，AI 会暂停或建议独立事项。

缺少接口契约或环境无法推进时写入“阻塞”，包含原因、已尝试方法和所需信息。解除后明确说明工单 ID 与解除条件，再恢复处理。

文件或工单依赖阻塞会关联具体文件或工单，查看时重新读取其当前状态和结果版本；历史保留当时原因。条件解除只提示可恢复，仍需明确恢复。必要验证缺失不能提交待验收，mock 不能代替声明为必要条件的真实联调；外部验收事项未完成时可以保留本单待验收，满足约定门槛后再验收。

## 5. 指挥 AI 验收、确认与回写

新工单提交时逐项附上实际结果、可阅读证据和证据指纹。表中已经写明标准、操作步骤和预期，指定验收人可以直接让 AI 去检查，不必自己先测一遍：

```text
$dev-handoff 验收工单 <工单ID>
```

AI 读取并固定当前交付版本，按标准运行测试、检查接口或操作可访问页面，逐项给出预期、实际结果、证据和结论。不能仅凭处理方写了“通过”就确认。缺环境、权限、工具或无法对应交付版本时，会列出无法验证项；没有可执行判据的主观要求交给你判断，不冒充已经验证。

这条短指令默认包含“全部通过就确认、有明确失败就退回并写明原因、无法验证项列出原因”，无需每次附加长说明，也不再机械地询问一次是否通过。有失败和无法验证项同时存在时，按明确失败退回，并一并列出无法验证项；没有失败但存在无法验证项时，保持待验收，不误报通过或失败。需要你决定的事项，AI 应说明具体缺口，而不是把整份验收重新交给你。

如果这次只想拿检查报告，明确限制：

```text
$dev-handoff 验收工单 <工单ID>，只检查，不回写
```

此时 AI 仍执行实际检查，但不写入确认、退回或完成记录；`查看验收材料` 则只读取材料，不执行检查。

如果你已经核对了 AI 的检查报告，或选择自己完成核对，也可直接确认已展示的版本：

```text
$dev-handoff 验收通过 <工单ID>
```

AI 只使用指定验收人的账号逐项确认，并把授权、实际观察和确认绑定同一结果版本；AI 执行的检查如实记录，不写成人亲自测试。确认后，原工作区的自动回写进程读取确认记录，核对需求、完整确认、原执行会话、代码指纹和依赖，再写入“已完成”，无需 codedroll 再发指令。实际验收人和确认时间写入工单，原处理人的回写动作另留日志。刚确认、尚未回写时仍显示“待验收”；只有回读到完成才算闭环。

自动回写需要处理方电脑保持运行、网络可用，通常每 60 秒检查一次，短暂网络故障会退避重试，最长等待 7 天。电脑关机或进程被终止期间不会回写；再次在原工作区让 AI“处理／继续”时，会恢复此前已启用且仍在等待的任务。代码、需求、账号或确认异常会停止并保留原因，不能强行完成。可说“查看自动回写 工单ID”只读检查状态，或“停止自动回写 工单ID”取消它。

**升级前已待验收的单**，由原处理方在原工作区说一次“启用自动回写 工单ID”；升级后新提交的业务单默认启用。等待超时或主动取消后，可明确重新启用；校验失败则先排查，重新验证提交新版本。手动兜底话术“回写已确认的验收 工单ID”仍保留，但不再是每单必说的一步。

业务材料可以跨账号、跨工作区验收，最终代码复核与完成回写仍须回到原处理账号和工作区。跨工作区的材料查看会明确标记尚未检查原代码，不跳过指纹保护。旧工单没有指定验收人和逐项标准时，继续沿用原处理账号、原工作区的原有流程。

代码或需求变化后须重新处理／验证，并对新版本重新验收。未满足要求时，可按已授权的失败分支退回，也可输入“退回 工单ID 原因”；AI 绑定已审阅版本及标准保存反馈，恢复到待对接。原处理人也可以撤回本人的待验收结果。重提始终产生新版本，旧确认不会自动复用。“通过并继续”只有在原工作区完成回写后才开始下一条。

不要直接在表格里把状态改成已完成来替代技能验收，那样不能生成受代码证据约束的验收记录。

### 5.1 给你和 codedroll 的日常业务话术

以下以**你发布并验收、codedroll 接手开发**为例；反向对接时交换角色。发布时明确实际验收人，AI 从成员表核对唯一账号，不默认把发布人当验收人。双方先各自接入同一张表，再在自己的仓库、自己的账号下对 AI 说。示例使用 Codex 的 `$dev-handoff`；Claude Code 换成 `/dev-handoff`。

把 `〈表名〉`、`〈ID〉` 等占位符换成实际值。“验收工单”会由 AI 自行读取并固定当前版本，无须手抄版本号；手动确认或退回中的 `〈完整版本〉` 使用 AI 本轮展示的值。双方自行把工单 ID 和本轮版本告诉对方，技能不会自动发消息。

正常流程：**发布 → 处理并启动自动回写 → 待验收 → 指挥 AI 逐项验收 → 确认后原工作区自动完成**。有明确失败则退回，修复重提后重新验收。

| 环节 | 你对 AI 说什么 | codedroll 对 AI 说什么 |
|---|---|---|
| 发布 | 先暂存本次交接代码，再说：`$dev-handoff 发布 〈表名〉，分配给 codedroll，由我验收。按可独立验收的交付拆单，写清交付范围、逐项验收步骤、预期结果和必要验证。` | — |
| 领取、处理 | 将发布返回的工单 ID 告诉 codedroll。 | `$dev-handoff 处理工单 〈ID〉；未分配时先领取。按约定完成开发和必要验证，逐项附实际结果与可阅读证据，提交待验收并展示完整结果版本。` |
| 让 AI 执行验收 | `$dev-handoff 验收工单 〈ID〉`，默认逐项检查并按结果确认或退回，无法验证项列出原因。 | 将待验收的工单 ID 和本轮结果版本告诉你，并提供约定所需的可访问环境和证据。 |
| 全部符合，确认 | 上一条已授权，AI 实际全部检查通过后直接确认。若之前只让 AI 检查，核对报告后再说：`$dev-handoff 验收通过工单 〈ID〉当前展示的版本 〈完整版本〉。` | 保持原处理电脑运行并联网，已启动的后台自动复核并回写。 |
| 有问题，退回 | 已授权时 AI 根据失败证据直接退回。也可补充手动反馈：`$dev-handoff 退回工单 〈ID〉版本 〈完整版本〉：标准 〈编号〉不符合；实际是〈实际表现〉，预期是〈预期表现〉，复现步骤是〈步骤〉。` | 等待退回记录写入；退回后恢复为“待对接”。 |
| 修复、重提 | — | `$dev-handoff 继续处理退回的工单 〈ID〉，按反馈修复并重新验证，逐项更新实际结果和证据，提交新的待验收版本并展示完整结果版本。` |
| 重新验收 | `$dev-handoff 重新验收工单 〈ID〉`，对当前新版本重新检查，沿用默认处理规则。 | 将新版本告诉你；旧确认仅保留为历史，不能用于完成新版本。 |
| 最终回写 | 无需再批准；共享工单显示“已完成”才算结束。 | 默认自动完成，无需发话。历史待验收单首次启用：`$dev-handoff 启用自动回写 〈ID〉`；异常时查看：`$dev-handoff 查看自动回写 〈ID〉`。 |

**“继续”不等于“验收通过”；“验收通过”后的确认也不等于已经回写完成。** 代码或需求变化后，重新处理或验证、提交新版本，再由指定验收人确认。不能在做完后缩小原验收范围，也不能用尚未满足的外部验收门槛换取提前完成。

### 5.2 日常业务验收与双账号联调的区别

两人使用不同账号处理业务单，仍然是日常业务验收。本文的“双账号联调”专指验证技能跨账号、跨工作区协议的测试流程。

| 对比 | 日常业务验收 | 双账号协议联调 |
|---|---|---|
| 目的与材料 | 核对真实业务交付、约定标准和实际证据。 | 使用明确标记的测试工单与隔离夹具，验证身份、版本和回写保护。 |
| 确认 | 指定验收人明确确认，或授权 AI 按业务标准实际检查、全部通过后确认。 | 两个真实账号按分阶段脚本执行；记录标为协议测试，不代表业务通过。 |
| 退回与重提 | 有实际问题才退回，修复后重新验收；没有问题则确认后回写。 | 第一轮确认后主动退回，重提后测试旧版本确认不能用于新版本。 |
| 最终回写 | 原处理工作区的后台默认复核并回写真实业务单，保留手动兜底。 | 退回重提脚本按阶段手动回写；自动回写联调使用独立入口，由后台完成后只读核验。报告只证明协议验证结果。 |

只有明确要做协议测试时，指定验收人才使用下面的话术：

```text
$dev-handoff 对共享表 〈URL〉的测试工单 〈ID〉执行双账号联调第一轮，确认当前版本后退回。这是协议联调，不是业务验收。
```

分阶段操作、第二轮和恢复方法见 [双账号联调入口](references/acceptance.md#更新已安装技能后继续联调)。普通业务“验收通过”不执行主动退回，也不运行这套测试脚本。业务单如果把真实接口联调约定为必要验证，仍须完成，不能拿双账号协议测试结果替代。

**验证自动回写**时使用另一组话术：

| 谁操作 | 可直接发给本人 AI 的话 |
|---|---|
| 原处理方准备 | `$dev-handoff 在共享表〈URL〉准备真实双账号自动回写联调，指定 codedroll 验收，启动后台并给出测试工单 ID。` |
| codedroll 验收 | `$dev-handoff 对共享表〈URL〉执行自动回写联调〈工单ID〉。` |
| 原处理方查看结果 | `$dev-handoff 查看自动回写联调结果〈工单ID〉。` |

这次通过后不主动退回，也无需再说“回写已确认的验收”。codedroll 实际检查三种夹具行为，通过后确认；原处理电脑的后台完成，最后一步只读取结果。准备完成不等于联调通过，必须等两个真实账号的确认与完成记录都核验成功。完整步骤见 [自动回写联调](references/acceptance-auto.md)。

## 6. 多账号、恢复和并发

每位协作者在各自工作区保留 `.dev-handoff-local/`，不要复制给对方。项目绑定 `.dev-handoff.json` 只含非敏感表信息，可以各自绑定相同 URL。

写入超时先让 AI 执行 sync 回读恢复，按工单键和事件键去重。不要清空检查点或改 key 重复发单。关闭聊天后在原账号、原工作区恢复处理中事项。

一个工作区同一时间只处理一条；可以保留多条互不影响的待验收结果。腾讯 API 没有跨机器的条件写原子锁，不要让两个会话同时领取或开发同一条工单。

第二台电脑首次接入后，按 [setup.md 的跨设备验收步骤](references/setup.md)验证实际访问、发布、领取与回写。两个模拟账号的自动化测试不能代替这一真实联调。
